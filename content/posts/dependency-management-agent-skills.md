过去几个月，我们团队一直在为复杂工作流构建技能——Bug 分诊、PR 治理、Sprint 报告——并通过 Claude Code 的插件市场和内部渠道分享。目标很直接：让团队和组织能够复用同样的问题解决能力。

但当我们真正尝试分发这些技能时，采纳率很低。对于简单、轻量的技能，分享没问题。但对于复杂的多工具工作流——那些解决最棘手问题的技能——在作者机器上完美运行的东西，到了别人手里不是报错就是被闲置。我们怀疑这不是我们团队特有的问题。任何试图在组织内规模化技能共享的团队，都可能撞上同样的墙。

所以我们问自己：为什么？

## 根因：依赖管理

在按照 [Repo-as-Agent](/posts/repo-as-agent/) 模式构建团队 Agent 的过程中，我们认为找到了根因：**依赖管理**。

一个技能不仅仅是一个 Markdown 文件。我们真正想分享的是**解决特定问题的能力**——但能力需要拆解成技能：用自然语言写成的程序，规定 Agent 该做什么、按什么顺序、用什么工具。技能有深浅之分：浅层通用的技能（比如"执行 git rebase"）传递起来毫不费力；深层的领域特定技能——编排多步工作流、包含分支逻辑和隐含上下文——分享起来就困难得多，而偏偏是这些技能在解决最棘手的问题。

和任何程序一样，技能有**依赖**——一组隐式的前提条件，必须全部满足它才能跑起来。我们梳理了自己的依赖清单，归纳出五个类别。它们不是逐层堆叠的关系——任何一个单独就能导致失败：

- **Agent 与配置** — Agent 运行时（Claude Code、Cursor、Cline）及其配置（思考模式、推理深度、Agent 团队等）。
- **模型** — 底层 LLM（Opus 4.6、Sonnet 4.5、Gemini、GPT 等）。
- **运行时与操作系统** — 语言运行时（Python、Go、Bash）、LSP 服务器，以及操作系统（macOS vs Linux）。
- **CLI 工具** — 技能调用的外部二进制文件（curl、jq、gh、oc、kubectl、helm、aws 等）。
- **凭证** — API token、kubeconfig 文件、webhook URL、pull secret 及其关联权限。

## 每个类别中的问题

每个依赖类别都是一个潜在的失败点。分享一个技能时，你其实在默认对方的环境和你的在五个维度上都一致。下面是各类别实际踩坑的情况：

**Agent 与配置不匹配：** 不同的 Agent 有不同的工具调用机制、权限模型和技能格式。为 Claude Code 编写的技能可能无法在 Cursor 中正确运行。即使在同一个 Agent 中，配置差异也会坑人：一个依赖子 Agent 委派的技能，如果接收者没有启用 Agent 团队功能，就会静默失败。不同的思考深度设置会对相同的提示产生不同质量的推理。

**模型差异：** 模型在能力上有差异——不仅跨供应商（Claude vs Gemini vs GPT），同一供应商的不同层级（Opus vs Sonnet）也不同，甚至同一层级的不同版本也有区别。在 Opus 4.6 上可靠运行的技能，在 Sonnet 4.5 上可能产生降级或错误的结果。在最近一次团队内的结对编程中，我们发现有些成员还在使用默认的 Sonnet 4.5 而不自知。这提醒我们，模型是一个容易被忽视的依赖——人们倾向于使用默认设置，很少检查它是否匹配技能的设计要求。

**运行时与操作系统分化：** Shell 脚本在 macOS 和 Linux 上行为不同（GNU vs BSD coreutils、`sed -i` 语法、`date` 参数）。不同的 Python 或 Go 版本引入微妙的不兼容。缺少 LSP 服务器会降低代码智能能力。

**CLI 工具缺失或不兼容：** 我们的 Agent 依赖 16+ 个二进制文件。即使一个简单的 Jira 技能也需要 curl、jq、python3 和两个环境变量（见依赖矩阵）。一个缺失的二进制文件就会导致整个技能失败。

**权限不对称：** 不同的工程师对不同的仓库有写权限、不同的集群访问级别、不同的管理员权限。一个用某人的 token 能正常工作的技能，换了别人的可能静默失败——或者更糟，部分成功。

## 采纳失败的心理学

这些断裂点不仅导致技术故障——它们还塑造人的行为。当有人分享一个复杂技能时，接收者不只是评估速度，还会权衡风险、稳定性和可控性。这在行为科学中有充分的文献支持：

- **技术接受模型**（Davis, 1989）：采纳取决于感知有用性和感知易用性。一个强大但依赖配置痛苦的技能不会被采纳。
- **损失厌恶**（Kahneman & Tversky, 1979）：人们对潜在损失的权重约为收益的 2 倍。一个坏掉的工作流比节省的时间感觉严重得多。这驱动了**现状偏见**（Samuelson & Zeckhauser, 1988）——手动操作感觉更安全。
- **自动化信任**（Lee & See, 2004）：信任取决于性能、过程和目的。未管理的依赖使性能不可预测，从而侵蚀信任。
- **算法厌恶**（Dietvorst et al., 2015）：看到自动化失败一次后，人们会显著降低使用意愿——即使它总体上优于人类。一个因缺少二进制文件而在首次尝试时失败的技能，基本上就宣告死亡了。

而且依赖对齐不可扩展。分享给 10 个人 → 对齐 10 个环境。更新技能 → 破坏全部 10 个。这就是"在我机器上能跑"的翻版——只不过现在那个程序是一个"技能"。

## 我们的方案：容器 + 实时 Agent

我们回到了软件工程解决依赖管理的老办法：**容器**。

我们的 Dockerfile 打包了一切：3 个运行时、16+ 个 CLI 二进制文件、两个 LSP 服务器、GitHub App 认证脚本，以及一个标准化的 Linux 环境——彻底消除操作系统差异。它是我们依赖文档的可执行版本，设计上保持同步。

然后我们通过 KubeOpenCode 的实时服务器模式更进一步：从容器镜像部署一个实时 Agent，团队成员通过 Web UI 或 CLI 连接——无需本地配置。Agent 自带依赖预装、工具预配置、模型锁定、上下文预加载。

**对于复杂工作流，分享 Agent 比分享技能更有效。**

## 待解的缺口：凭证

容器解决了五个依赖类别中的四个——Agent、模型、运行时和 CLI 工具。但**凭证**仍然是按人、按权限的——不同的工程师对不同的仓库有写权限、不同的集群访问级别、不同的管理员权限。

理想情况下，一个实时 Agent 应该拥有自己的身份，并具有明确定义的权限边界。这目前还不存在，我们认为这是整个 Agentic 工程生态系统需要解决的问题。

## 结论

共享技能对于简单、通用的任务效果很好。但对于复杂的、团队特定的工作流，仅靠一个技能文件是不够的——它依赖于五个类别的隐式需求（Agent、模型、运行时、CLI 工具、凭证），必须全部对齐才能让能力真正生效。任何一个类别的不对齐都会导致失败，而失败会侵蚀信任。我们通过将依赖打包进 Dockerfile 并通过 KubeOpenCode 部署实时 Agent 解决了五个中的四个，让团队分享的是 Agent——而不仅仅是技能。剩下的挑战是凭证管理：赋予 Agent 自己的身份和明确的权限边界。我们认为这是 Agentic 工程生态系统的下一个前沿。
